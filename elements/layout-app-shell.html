Every signed-in page renders into this frame — you don't opt in. Switch to another shell only for login, print/export, or system pages.

Do

  • Use the Layout shell for every authenticated app page (the default — no route override needed).
  • Keep the content panel the only scrolling region.
  • Mount global/portal UI (toasts, OmniBox) at the overlay layer, above the content.

Don't

  • Don't put the breadcrumb/back in the Header — that lives in the page header.
  • Don't add a second scrolling container inside the content panel.

Where it’s used

  • Every authenticated in-app page — the default for ~all routes.
  • Drop the chrome via a different shell: login, report export, upgrade/restore.

Decision flow

  1. Start EVERY authenticated product screen here — the app shell is the outermost frame (top nav bar + left icon rail + content region). It is not optional chrome; it's the frame the page mounts into.
  2. Full-bleed page WITHOUT the shell (login, error, print, embedded/public view)? -> use a bare layout (LoginLayout/EmptyLayout/PublicLayout), NOT the app shell.
  3. Need a settings-style secondary side menu inside the content? -> compose layout-screen-regions (a left settings panel), don't fork the shell.
  4. The shell is fixed: don't recreate the top bar / icon rail per page — mount your screen into its content region.

Related

Structural reference, not interactive. In the product the regions map to landmarks — NavBar = <nav>, Header = <header>, content = <main>; the content panel is the only scroll container, so focus order is nav → header → content.

Known a11y issues

  • The overlay layer (toasts/OmniBox) must manage focus + ESC at the product level.
