Do

  • Use FlotoPaginatedCrud for fetched lists
  • Server-page large datasets
  • Put row actions in a kebab cell; multi-select via the bulk bar
  • Keep the header visible in empty/loading states
  • [element] Give rows a stable `id`; drive rich cells via each column's `type`; persist inline edits from the `save` event
  • [element] Use group-collapsible="false" for a static report grid; `tree` (children) for real hierarchy

Don't

  • Don't use a grid for a handful of static key/values (use obs-key-value) or big-value metrics (use obs-metric-list)
  • Don't client-load huge datasets (server-page)
  • Don't hand-roll selection/paging — MGrid/FlotoPaginatedCrud own it
  • Don't inline-edit a whole record with validation — use a drawer/modal form; keep inline editing to a few quick fields
  • Don't add an outer surrounding border — the product grid is borderless (bordered = internal cell grid only)

Decision flow

  1. Just a few static key/values for ONE record, not a dataset? -> obs-key-value (a definition/detail list), NOT a grid.
  2. A short list of big metric/KPI values (value + unit + label), not rows-of-records? -> obs-metric-list, NOT a grid.
  3. Need to fetch + paginate a list with CRUD? -> FlotoPaginatedCrud (wraps MGrid; handles fetch/paging/search/filters). [element] obs-table with columns + rows.
  4. Have data already in memory to show in a table? -> MGrid with :data + :columns. [element] obs-table columns + rows.
  5. Large/server dataset? -> MGrid server paging (external-take/external-skip + total-count + @data-state-change).
  6. Rows edited in place (no separate form/drawer)? -> [element] obs-table `editable` (a pencil per row; columns with editable:true become obs-inputs, Save/Cancel). For a full record form use a drawer/modal instead.
  7. Rows need actions? -> a row-actions kebab cell (FlotoGridActions); multi-select -> selectable + the bulk-action bar.
  8. Rows have drill-down detail? -> expandable + the detailRow slot.
  9. Genuinely hierarchical (parent/child levels)? -> [element] obs-table `tree` (rows carry a `children` array; chevron + indent per level).
  10. Rows bucketed under group headers with counts? -> `grouping` ([element] group-by). If it's a static report where children never collapse (no chevron, all rows always visible) -> add group-collapsible="false" (the pivot/report grid).
  11. Columns need rich rendering (status tag, severity dot/ring, tags, sparkline, heat cell, percent bar, type icons)? -> per-column `type` on the column (cell-types).

Usage rules

crudList
Use when: a fetched, paginated, searchable list (the default)

expandable
Use when: each row has detail

basic
Use when: You have a plain dataset to render as columns + rows with sortable headers — either data already in memory (`MGrid` with `:data` + `:columns`) or a fetched/paginated/searchable list page (the default, via `FlotoPaginatedCrud`, which wraps MGrid and owns fetch/paging/search/filters). The main `.k-grid` data-grid header (transparent, UPPERCASE, 600) is the standard chrome.
Don't: Don't use a grid for a handful of static key/values — use a definition list / cards instead. If rows need multi-select bulk operations use `selectable`; if each row has drill-down detail use `expandable`; if rows must be grouped with counts use `grouping`; if the dataset is large/server-driven use `pagination` with server paging.
e.g. Settings list views and inventory monitor lists rendered via FlotoPaginatedCrud; drill-down sub-tables and preview grids rendered via MGrid :data :columns.
grouping
Use when: Rows should be bucketed under group headers with per-group counts, and each band can COLLAPSE. In the product drive it with `default-group` (the grouping column(s)). [element] obs-table: `group-by="<columnKey>"` renders a grey group-header band with a chevron + count; click to collapse/expand. Hide the grouping UI with `.hide-grouping` when needed.
Don't: Don't use grouping to show nested record hierarchy — that's the `tree` variant. If the bands must NOT collapse (a static report where all child rows stay visible and there's no chevron) use the `pivot` variant (group-collapsible=false). For a flat sorted list, plain `basic` is enough.
e.g. Alert / event lists grouped by a column (e.g. by severity or source) with a count badge per group; [element] group-by="env" buckets monitors under Production / Staging.
cell-types
Use when: Columns need rich, non-plain-text rendering. Each column renders through a named slot (`status`, `name`, `tags`, `severity`, `value`, `duration`, `action`, `monitorType`, `timestamp`, `count`, …), so a cell can be a status tag, a severity dot, tags, a sparkline, a color-coded threshold cell (`color-coded-cell.vue`, heatmap-style / `relative-percent` inline bar), or a row-actions kebab (`FlotoGridActions`).
Don't: Don't reach for custom cell slots when a column is plain sortable text — leave it as `basic`. Don't put a bulk multi-select checkbox here (that's `selectable`) or the row expander (that's `expandable`); those are dedicated props/columns, not cell slots.
e.g. Monitor grid cells: a status tag (MStatusTag), a severity dot, tags, a value sparkline, and a trailing kebab cell (FlotoGridActions) for per-row actions.
pagination
Use when: The dataset spans multiple pages. Use client paging (`paging` + `default-page-size`) for in-memory lists; use server paging (`external-take` / `external-skip` + `total-count` + `@data-state-change`) to fetch only the visible page for large/server-driven datasets. FlotoPaginatedCrud wires this up for fetched list pages.
Don't: Don't client-load huge datasets — server-page them. Don't hand-roll paging controls; MGrid / FlotoPaginatedCrud own paging, sort, and filter. For live socket/widget-pushed feeds use the streaming grid (`api-socket-grid`, no paging) rather than paginating.
e.g. Large inventory / settings list pages server-paged through FlotoPaginatedCrud, fetching only the current page from the API.
tree
Use when: Data is genuinely hierarchical — parent rows with nested child rows across levels. Use the `tabular-content-grid` tree (`expandable` with a `detailRow` of nested child rows, chevron + indentation per level).
Don't: Don't use `tree` for a single row's flat detail panel — plain `expandable` is enough. Don't use it for flat grouped buckets (`grouping`) or cross-tab metric summaries (`pivot`).
e.g. SNMP OID / MIB trees — expand a parent OID to reveal indented child OID rows level by level.
pivot
Use when: A static report/pivot grid: rows grouped under band headers that NEVER collapse — no chevron, no count, every child row always visible. [element] obs-table: `group-by="<key>"` + `group-collapsible="false"`. NOTE: this is a custom-element boolean attribute, so it must be the string "false" (group-collapsible="false") — omitting it leaves grouping collapsible (the default).
Don't: Don't use `pivot` for ordinary grouped list rows that a user collapses/expands — that's `grouping` (the collapsible default). Don't use it for a single-record transposed key/value view — that's obs-key-value — or a big-value metric list — that's obs-metric-list.
e.g. A report widget grouping monitors by environment where every row must stay visible (no expand/collapse) — group-by="env" group-collapsible="false".
editable
Use when: A user edits row values IN PLACE, without opening a separate form/drawer/modal — quick edits to a couple of fields. [element] obs-table: set `editable`, and mark each editable column with `editable:true`. A pencil appears per row; clicking it turns that row's editable columns into obs-inputs with Save / Cancel (obs-link). Listen to `save` ({id, values}) to persist, `canceledit` to discard.
Don't: Don't use inline editing for a full record with many fields, validation, or related sections — use a drawer or modal form (obs-drawer / obs-modal) instead. Don't make identity/computed/status columns editable (leave those as display cells).
e.g. A monitor list where an operator quickly renames a monitor or fixes its IP/owner inline, then Save — without leaving the list.
styleVariants
Use when: You need to tune the grid chrome for a context. [element] obs-table: `variant="bordered"` (internal column+row grid, no outer frame) for a dense data grid; `variant="borderless-rows"` (no row dividers, airy spacing) for a light widget list; `header-style="tinted"` for the item-list tinted header bar; `hide-header` for compact widget grids with no header row.
Don't: Don't add an outer surrounding border — the product grid is borderless (bordered only draws the internal cell grid). Don't mix hide-header with sortable headers (there's no header to click).
e.g. A compact dashboard widget grid using borderless-rows + hide-header; a dense settings table using variant="bordered".
header-style
Use when: header-style="default" (transparent header + bottom rule) for LIST/report screens — this is what the product uses. header-style="tinted" (grey band) only for a dense item-list table where the product uses the tinted header.
Don't: tinted on a normal list/report grid — it paints a grey band the product does not have (both values pass conformance, so this wrong guess is invisible to automated checks).
Must: default is the list-screen norm (it is also the element default — omit the attribute).
e.g. <obs-table columns=... rows=...></obs-table> (default header — correct for list screens)
cell-content
Use when: a column needs a real control/link, not text: type="switch" (boolean cell → obs-switch), type="icon" (clickable obs-icon; cell = icon name or {icon,label}), type="link" (cell = {text,href,icon?} or a string), type="button" (cell = {text?,icon?,variant?}). Activating any of them emits `cellaction` {id,key,type,value}.
Don't: passing raw <obs-*> markup as a cell VALUE — cell values are escaped as text. Use the typed cell instead.
Must: handle `cellaction` to react. For a two-control cell (the product NAME column: a ★ that favourites + text that opens), use type="link" with a leading icon and read `part` in the payload — `part:"icon"` (the icon was clicked) vs `part:"text"` (the label was clicked).
e.g. columns:[{key:"name",type:"link"}] with row.name={text:"Report 1",icon:"star"} → @cellaction gives {type:"link",part:"icon"|"text",id,key,value}
sticky-header
Use when: the header should stay visible while the body scrolls — set sticky-header AND max-height="<px>" for a self-contained scroll box.
Don't: sticky-header without a bounded height (nothing scrolls) unless an ancestor is the scroll container.
e.g. <obs-table sticky-header max-height="420px" ...>
