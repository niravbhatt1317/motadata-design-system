Severity Heatmap

The product's Infrastructure-Heatmap honeycomb (PlainHeatMap) — one hexagon per monitor, each filled with its severity colour, packed into a honeycomb grid. Hovering a hex raises the product tooltip (monitor name/IP + location + a severity pill). The DS chart library flags "heat-map" as a CUSTOM-ENGINE type (data-only, no serializable renderer); this element IS that renderer, ported 1:1 from the product's heatmap-single-group.vue — a border-coloured hex box with a 1px-inset severity cell (the thin outline), size x 1.1547 height and a size x 0.2885 honeycomb pull-up.

PropTypeDefault
cells
The monitors to plot — one hex per entry. Accepts an array of plain severity STRINGS (['down','critical','up', ...]) OR an array of OBJECTS { severity | sev, name | label | ip, location | sublabel | sub }. Each object is normalised to { sev (lowercased), name, sub }: severity/sev -> the hex fill var(--severity-<sev>); name/label/ip -> the tooltip title; location/sublabel/sub -> the tooltip subtitle. A string cell has no name, so it renders colour-only with no hover tooltip. Also accepts a JSON STRING of that array (it is JSON.parsed) — this is how the static showcase passes it as an attribute. Mirrors the DS heat-map fixture's result.data shape.
array | string"[]"
size
Hexagon WIDTH in px. Height is derived = size x 1.1547; margin = floor(size/17); honeycomb pull-up (negative bottom margin) = size x 0.2885. Strings are coerced (+size); a falsy/invalid value falls back to 22. Scale the whole grid by changing this one number.
number | string22
max
Truncation cap. 0 (default) shows ALL cells. When > 0, only the first N hexes render and a "+N more" pill is appended for the remainder (remaining = total - max, clamped to >= 0). Strings are coerced (+max).

A large fleet of monitors where the shape/spread of severity across the whole population matters more than any single row — worst severities banding at the top, healthy (up) filling the body. The colour encodes each monitor's severity; the hover tooltip carries its identity (IP + location) for spot-checking.

Do

  • Use it for the severity spread of MANY monitors — one hex per monitor, colour = severity.
  • Pass object cells with a name/ip + location so the hover tooltip can identify each monitor.
  • Let the fill read from var(--severity-<level>) so the honeycomb follows light + dark theme.
  • Cap very large fleets with max="N" (a "+N more" pill) instead of overflowing the widget.
  • Scale the whole grid with size (hex width); keep the derived geometry — don't hand-tune per-hex margins.
  • Order/band the data meaningfully (worst severities first) so the coloured shape tells a story, like the product.

Don't

  • Don't use a honeycomb for a small list that needs per-row detail — that's a table.
  • Don't use it for a single value-against-total figure — that's a gauge.
  • Don't rely on colour alone to convey a specific monitor's status — the identity lives in the hover tooltip, which is mouse-only (see a11y).
  • Don't hardcode hex fills — pass a real severity so the colour is information, not decoration.
  • Don't dump thousands of hexes unbounded into a small widget — cap with max or pre-slice.

Decision flow

  1. Showing the severity spread across MANY monitors at a glance (the shape of the fleet's health)? -> obs-severity-heatmap honeycomb.
  2. Only a handful of items, and you need per-row columns/detail (IP, type, actions)? -> a table, not a honeycomb.
  3. A single value against a group total, coloured by status? -> an obs-gauge dial (or a row of them), not a honeycomb.
  4. A trend over time or multiple series? -> a line/area chart from the data-viz family.
  5. Too many monitors to render comfortably? -> cap with max="N" so it shows the first N + a "+N more" pill (or pre-slice the data).
  6. Need each hex to identify its monitor on hover? -> pass OBJECT cells with name/ip + location; bare severity strings render colour-only (no tooltip).

Usage rules

infra-honeycomb
Use when: a dashboard needs the at-a-glance severity spread of a large monitor fleet — worst severities banded at the top, healthy up filling the body
Don't: for a short list where the reader needs columns/detail per monitor (use a table), or a single aggregate figure (use a gauge)
e.g. <obs-severity-heatmap cells='[{"severity":"down","name":"172.16.8.113","location":"MB_Location_5"}, ...]' size="22"></obs-severity-heatmap>
hover-identity
Use when: the reader will want to spot-check individual monitors — give each cell a name/ip and a location so the hover tooltip shows "172.16.8.113 / MB_Location_5 / Warning"
Don't: when you only have the severity per cell (bare strings render colour-only, which is fine for a pure density view)
e.g. cells: [{ severity: 'warning', name: '172.16.8.113', location: 'MB_Location_5' }] -> hover shows the name + location + a warning pill
truncated
Use when: the fleet is larger than the widget can comfortably show — cap it with max so a bounded preview + a "+N more" pill renders instead of an overflowing grid
Don't: when the whole population must be visible (the banding pattern is the point) — then render all cells and size the container instead
e.g. <obs-severity-heatmap max="48" cells='[ ... 200 cells ... ]' size="18"></obs-severity-heatmap> -> 48 hexes + a "+152 more" pill
compact
Use when: a small honeycomb of a handful of monitors must fit a tight widget or an inline health strip — shrink the whole grid with a smaller size (14-18) so the hexes interlock in a dense summary rather than the full-size dashboard grid
Don't: for hundreds of monitors where the banding shape is the point (use the full infra-honeycomb at size 22+), and don't hand-tune per-hex margins to force it small — change only size (the height size x 1.1547 and pull-up size x 0.2885 are derived from it)
e.g. <obs-severity-heatmap size="14" cells='[{"severity":"up","name":"172.16.8.101","location":"MB_Location_1"}, {"severity":"warning","name":"172.16.8.102","location":"MB_Location_2"}]'></obs-severity-heatmap>
bare-cells
Use when: you only have the severity per monitor and want a pure colour-only density view — pass plain severity STRINGS (['down','critical','up', ...]) so each hex fills with var(--severity-<level>) and the honeycomb reads as a spread of colour with no hover tooltip
Don't: when the reader needs to spot-check individual monitors on hover — a bare string has no name/location so no tooltip renders; pass OBJECT cells { severity, name, location } instead (the hover-identity card)
e.g. <obs-severity-heatmap cells='["down","critical","warning","up","up","up"]' size="18"></obs-severity-heatmap> -> colour-only hexes, no tooltip
size-scaling
Use when: the honeycomb must fit its container — pick size (hex width px) to trade density for legibility (14-18 dense, 22 default, 26+ roomy)
Don't: sizing per-cell or hacking margins; the geometry (height size x 1.1547, pull-up size x 0.2885) is derived from this one number
e.g. size="22" (dashboard) vs size="14" (dense strip)

A presentational density map — each hex is a coloured, non-focusable div; severity is conveyed by colour (var(--severity-<level>)) and monitor identity only by a mouse-hover tooltip. Non-interactive to the keyboard.

Known a11y issues

  • Colour-only encoding: a cell's severity is communicated purely by its fill; there is no per-hex text or aria-label, so the meaning is lost to screen readers and to colour-blind users. The hover tooltip is the ONLY text alternative (it names the severity, e.g. "Warning") — but it is mouse-only, so the text alternative is unreachable by keyboard/AT and absent for bare-string cells.
  • The hover tooltip is mouse-only (mouseenter/mouseleave) and pointer-events:none — it can't be reached by keyboard or focus, so its name/location/severity content is unavailable to assistive tech.
  • The hexes are plain <div>s with no role/tabindex — the honeycomb is not keyboard-navigable and exposes no accessible name or summary of the population.
  • The 1px inset outline is the only separator between adjacent same-severity hexes; at small sizes low-contrast severities can be hard to distinguish.

Used in the Alert-Summary dashboard Infrastructure Heatmap.
  • Colour + hover only — no per-hex aria-label and the tooltip is mouse-only, so severity + identity are visual-only (see a11y).
  • The tooltip is anchored by pixel offsets within the honeycomb container and renders to the hex's right; near the right edge of a narrow widget it can clip (no flip/collision handling).
  • severity is not enum-validated — an unknown level yields var(--severity-<unknown>) which resolves to nothing, so that hex fills with no colour (transparent over the border box). Pass a known severity.
  • No virtualisation — every cell is a real DOM node; a very large unbounded fleet is heavy to render (use max or pre-slice).
