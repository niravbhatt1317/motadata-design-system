Side Menu

The in-module SECTION navigation panel — a searchable, collapsible left menu. ONE element with a `mode` axis folding the product's five side-menu forms: settings (THE Settings menu — left-menu.vue: a MULTI-OPEN collapse with the expand chevron on the RIGHT, full-width dividers between sections, and children as an indented ROUNDED-highlight menu), sections (a leaner accordion form — LEFT chevron + an inset --primary left-rule active), categories (dashboard picker, count tags), tree (Log/Topology N-level hierarchy with type icon + count badge), and list (report/saved-views flat list, optional ★ favourite). Data-driven via a recursive `items` model; optional top segmented `tabs` + a search box. NOT the module rail (obs-sidebar), NOT sibling views (obs-tabs), NOT the faceted checkbox filter (a vertical Filter). SIZING: the element is width:100% (fills its container) — set the container WIDTH per mode (settings|sections ~15% / categories ~30vw / tree|list ~20%); see `sizing` + usageRules[mode].width. The element OWNS its own chrome — a flush white panel with a RIGHT border/divider, its own internal padding, and an automatic TOP/BOTTOM scroll FADE (content dissolves into the panel at whichever edge can still scroll) — so the host column adds NEITHER a border NOR padding (they would double up).

  • default — the default (footer) slot at the bottom, below the list — e.g. a "+ New Category" action. Adds no height when unused.

Do

  • Render it as a flush WHITE panel filling its column — don't put it on a gray surface or in a rounded card.
  • Pick the `mode` for the shape of your data — `settings` (the product Settings menu) / sections / categories / tree / list.
  • Feed a recursive `items` model; set `active` to the current leaf; child items may carry an `icon`/`logo`/`count`.
  • SIZE THE COLUMN ONLY (a fixed width + min-height:0). The component owns its RIGHT border, internal padding, and the top/bottom scroll fade — add none of them on the host.
  • Reuse the header slots for mode chrome — `tabs-action` (＋), `search-action` (toggle); the search is a real obs-input.
  • Wire `select` to filter the grid/route; `tab`/`search` as needed. For the Settings page pair `settings` mode with the obs-page-header `menu-toggle` (show/hide).

Don't

  • Don't add a `border-right` OR `padding` to the side-menu host/column — it already draws its own right divider + internal padding + scroll fade; a second one doubles the rule and the gutter (the starter hit this exact bug).
  • Don't give it a gray background or a rounded/bordered card — it's a flush white panel (product = background:none, radius:0).
  • Don't use it for top-level modules (obs-sidebar) or sibling views (obs-tabs).
  • Don't use it as a faceted checkbox filter — that's a vertical Filter.
  • Don't hand-roll the accordion/tree — reuse obs-side-menu.
  • Don't hardcode colours — active is --left-menu-text-hover-color on --left-menu-hover-bg (settings) / --primary on --code-tag-background-color.

Decision flow

  1. THE Settings menu (a module section nav with icons, RIGHT chevrons, dividers between sections, expanding to a rounded-highlight sub-menu)? -> obs-side-menu mode="settings".
  2. A leaner/compact section accordion (left chevron, an inset left-rule active, no per-section dividers)? -> mode="sections".
  3. A category picker with COUNTS (Dashboard categories → dashboards)? -> mode="categories".
  4. An N-level HIERARCHY with type icons + counts (Log types, Topology tree)? -> mode="tree".
  5. A flat LIST of saved views / reports (optional favourites)? -> mode="list".
  6. Switch between top-level MODULES? -> obs-sidebar, NOT the side-menu.
  7. Switch between sibling VIEWS of the same page? -> obs-tabs.
  8. A faceted CHECKBOX filter panel? -> a vertical Filter (Filters family), not a side-menu.

Usage rules

settings
Use when: the Settings module (or any module whose left nav is a searchable, multi-open list of icon+name sections that expand to a sub-page menu). Pair with obs-page-header menu-toggle to show/hide it.
Don't: top-level module switching (obs-sidebar), sibling views (obs-tabs), or a compact accordion where you want a left chevron + inset-rule active (use sections).
e.g. Settings: My Account (expanded → My Profile active) · User Settings · System Settings · … (18 sections, each with its product icon + a right chevron; full-width dividers between sections).
sections
Use when: a compact in-module section accordion (left chevron, inset-rule active) — when you specifically do NOT want the Settings menu chrome (right chevrons / dividers / rounded child)
Don't: the real Settings menu (use settings) · top-level module switching (obs-sidebar) · sibling views (obs-tabs)
e.g. Settings: General / Monitoring / Users & Roles → sub-items, Monitoring expanded
categories
Use when: grouped items with counts, expand to children (dashboard picker)
Don't: a flat list (use list) or a deep hierarchy (use tree)
e.g. My Favorite (7) / Server (6) → child dashboards
tree
Use when: a multi-level hierarchy where nodes carry a type icon + a count (log types, topology)
Don't: a 2-level section menu (use sections/categories)
e.g. Syslog 57.25M / Linux 9.86M → Linux Syslog 9.61M
list
Use when: a flat list of saved views / reports, one active, optional favourites
Don't: when items nest (use tree/sections)
e.g. All Reports (active) · ★ Favorites · user categories
with-tabs
Use when: the panel switches between named scopes (Dashboard/NOC, Metric/Log/Flow)
Don't: a single-scope menu (omit tabs)
e.g. Metric / Log / Flow / Trap / Audit tabs above a saved-views list
with-search
Use when: the list is long enough to need filtering (default on)
Don't: a short fixed menu (set search=false)
e.g. typing 'linux' filters + auto-expands the tree
surface
Use when: always — the in-module side menu is a FLUSH WHITE panel (var(--common-widget-bg)); it fills its column edge-to-edge.
Don't: a gray/tinted surface or a rounded bordered card. Do NOT wrap it in a gray container, and do NOT set its background to --page-background-color / --common-main-bg (those are the PAGE, which is grey in a real app — the menu would go gray).
Must: keep it white and flush with a RIGHT divider only (its OWN border-right) — no card border/radius, AND the host column adds no border/padding of its own (the component already provides both). Matches the product settings menu (full-height column divided from content by a single right border).
e.g. <obs-side-menu mode="sections" items="..."></obs-side-menu> in a full-height left column — white, borderless.
