Filters

The product's filtering components, grouped by ARCHETYPE (not by the screen they sit in). Four distinct kinds: the Expression builder (nested AND/OR query builder), the Filter bar (inline chips), Quick filters (preset menu), and the Filter row (multi-selects + Reset/Apply). These are molecules; the Toolbars (organisms) compose them.

Do

  • Use the Expression builder for real query logic (groups + AND/OR + typed operators).
  • Use the Filter bar for a compact chip filter over a grid.
  • Use Quick filters for common one-click presets.
  • Use a Filter row for a small fixed set of facets.

Don't

  • Don't hand-roll a condition builder — use FiltersContainer.
  • Don't put plain search here — that's the Input search type.
  • Don't duplicate a filter across screens — it's one molecule; compose it in a Toolbar.

Decision flow

  1. Complex AND/OR conditions across multiple groups? -> Expression builder (FiltersContainer, 32×).
  2. A compact inline chip bar over a grid? -> Filter bar.
  3. One-click saved/preset filters? -> Quick filters.
  4. A few simple multi-selects + Apply/Reset? -> Filter row.
  5. Plain text search of a list? -> the Input 'search' type (181×), not a Filter.

Usage rules

expression-builder
Use when: You need real query logic — complex AND/OR conditions across one or more nested groups with typed operators. This is the most-used filter (FiltersContainer, 32×): a FilterTrigger input opens an MPopover with Pre/Post Filters tabs, 'Group(s) matching All/Any' → groups (Include/Exclude, matching All/Any) → conditions (field · operator · value, type-aware, Between → From/To), Add Condition (max 3) / Add New Group, and a Reset / Clear / Apply footer where Apply emits the query and renders it back into the trigger.
Don't: Don't use for a compact chip filter over a grid (→ Filter bar) or a small fixed set of facets (→ Filter row). Don't hand-roll a condition builder — always compose FiltersContainer. For plain text search of a list, use the Input 'search' type, not this.
e.g. The nested AND/OR query builder popover opened from a search-style FilterTrigger over a grid — the 32× FiltersContainer usage, with Pre/Post Filter tabs and Include/Exclude groups matching All/Any.
filter-bar
Use when: You want a compact inline chip filter sitting directly over a grid. The Filter bar (FlotoFilterBar, ~50×) renders field·operator·value chips (default-chips declared by the module via defaultChips have no ×), a '+ Filter' button, a Match All/Any toggle, and Clear All; chips scroll horizontally while the segment picker floats position:fixed so it never clips.
Don't: Don't use when you need nested groups or AND/OR logic beyond a flat Match All/Any (→ Expression builder). Don't use for one-click presets (→ Quick filters) or a slide-in facet panel (→ Filter row). Not for plain text search (→ Input 'search' type).
e.g. The inline chip bar over a data grid where the module seeds leading default-chips (e.g. Groups/Types/Severity via defaultChips) and users add field·operator·value chips with Match All/Any — the ~50× FlotoFilterBar usage.
bar-quick-filters
Use when: kind="bar" over a list where a few fields are the primary, always-visible facets (e.g. Groups / Types / Severity on the Monitors/Inventory grid). Pass those field keys as `quickFilters` and they render as STANDING pills before the '+ Filter' chip: an empty pill shows just the category label and opens that field's value picker on click; a set pill shows the value(s) with a +N count and an × to clear. The pills persist even when empty, so the primary facets are always one click away while other fields are still added via '+ Filter'.
Don't: Don't use quickFilters when the bar should show only whatever the user has actively added (→ plain kind="bar", which shows active chips + '+ Filter' only). Don't use for nested AND/OR groups (→ Expression builder), one-click saved presets (→ Quick filters), or a slide-in facet panel (→ Filter row). Don't preset a quick key that isn't in `fields` — it is silently dropped.
e.g. <obs-filters kind="bar" :fields.prop="fields" :quick-filters.prop="['group','type','severity']"></obs-filters> → a Groups / Types / Severity / + Filter row; click Groups to pick group values, the pill then reads 'Groups = MySQL (+2)' with an ×.
quick-filters
Use when: You want to expose common, one-click preset filters. Quick filters (filter-quick-menu) is a thumbs-up button that opens a panel of PRESET filters as { key, label, condition }; picking one immediately applies that condition.
Don't: Don't use when users must author arbitrary conditions or groups (→ Expression builder) or maintain an evolving chip set over a grid (→ Filter bar). Not for facet multi-selects with Reset/Apply (→ Filter row).
e.g. The thumbs-up preset menu beside a grid toolbar offering saved one-click filters ({ key, label, condition }) — click a preset to apply its condition instantly.
filter-row
Use when: You have a small, fixed set of facets to filter a list — a few multi-selects (e.g. Groups / Severity / Tags) plus Reset/Apply and a close ×, presented as a slide-in over the list.
Don't: Don't use for real query logic with nested AND/OR groups (→ Expression builder), for an inline chip bar over a grid (→ Filter bar), or for one-click presets (→ Quick filters).
e.g. The slide-in Collection Filters panel over a monitoring list — a few multi-selects (Groups/Severity/Tags) with Reset/Apply and a close × (pattern e.g. metric-collection-filters.vue).
vertical-filter
Use when: You need a faceted left-panel sidebar that filters (not navigates) a grid. The vertical filter is a search box atop collapsible MCollapse groups, each row a checkbox + optional status/type icon + label + count; checking rows narrows the grid. Used across APM Explorer, APM Error Tracker, RUM Sessions, and a richer NCM Explorer variant.
Don't: Don't confuse it with a Navigation side menu — it filters, so it lives in Filters (cross-referenced from Navigation → Side menu). Don't use it for a compact inline chip filter (→ Filter bar) or nested AND/OR logic (→ Expression builder).
e.g. The APM Explorer / RUM Sessions left-panel faceted sidebar — a search over collapsible checkbox+count groups (with status/type icons) that filters the results grid; NCM Explorer uses the richer variant.
bar-wiring
Use when: kind="bar": pass fields + value (active conditions) + match (all|any); listen to `change` for {conditions, match}.
Don't: seeding value as an ARRAY via the el.value PROPERTY at mount if you are on <0.1.150 (it hit the vanishing-chip bug). Fixed now; array or string both work.
Must: read the `change` payload as {conditions, match} — it is NO LONGER a bare conditions array. `el.value` still reflects the conditions JSON.
e.g. <obs-filters kind="bar" fields=... value=... match="all" @change="e => { const {conditions, match} = e.detail[0] }">

Known a11y issues

  • SF-001 focus ring on chips/selects/buttons.
  • Icon-only triggers (thumbs-up, chip ×, row ×) need accessible names.
  • Each quick-filter pill is a real <button> whose text IS its accessible name (the field label, e.g. 'Groups'); a set pill's × has its own accessible name to clear that filter.
