Anywhere the user picks or drags a metric to build a chart / widget or a query: pick a monitor, then ⊕ / drag a counter from the searchable list (widget builder, metric explorer, alert/report metric fields).

Do

  • Use it to AUTHOR a visualization — pick a monitor, then ⊕ or drag a counter onto a chart / widget.
  • Load the monitor’s counters on `select-monitor` and feed them as the flat `counters` list.
  • Use `embedded` on a monitor-detail screen (the monitor is already known — no monitor tabs / Select Monitor).
  • Wire `add` (⊕) and `drag` to add the counter to your chart; both then remove it from the list.
  • Add monitors with the "+" (a new blank tab); close extras with a tab’s × (shown only when there is more than one).

Don't

  • Don’t use it as a generic dropdown — that’s obs-select; or a bare monitor table — that’s obs-grid-select.
  • Don’t confuse it with navigation — it looks like obs-side-menu but AUTHORS a value (a counter to plot), it doesn’t route.
  • Don’t treat the counter rows as a persistent selection — they are ADD / DRAG actions (there is no selected state).
  • Don’t hardcode colours — it uses tokens (border / neutral / primary / text).

Decision flow

  1. The metric-explorer picker (monitor tabs → Select Monitor grid → Metric/Instance/Saved View → counter list)? -> obs-metric-picker.
  2. Just a generic single-value dropdown? -> obs-select, NOT this.
  3. A standalone monitor TABLE picker (no counter list)? -> obs-grid-select (this composes it as the Select Monitor control).
  4. NAVIGATING between pages/sections (it looks like a list too)? -> obs-side-menu — that navigates; this selects a value.
  5. Comparing several monitors? -> pass several ids in `selected` → one closable tab each; the + adds more via the grid picker.
  6. Building a widget (add/drag counters onto a chart)? -> keep can-add on (default) — the ⊕ + 4-way drag per row.
  7. Instance-based monitor (disks / interfaces)? -> keep the Instance sub-tab (views default includes it).
  8. Counter rows are ADD/DRAG actions (⊕ to add, drag onto a chart) — NOT a persistent selection. Taking a counter removes it from the list; emits add / drag.
  9. Already on a specific monitor’s detail screen (the monitor is fixed)? -> `embedded` hides the monitor tabs + Select Monitor and shows just the Metric/Instance/Saved View tabs + counter list.

Usage rules

explorer
Use when: the metric explorer / widget builder — pick a monitor, then a counter to plot
Don't: a simple flat single-select (obs-select) or navigation (obs-side-menu)
e.g. monitor xen75 cluster → Metric tab → ⊕ citrix.xen.cluster.cpu.cores
multi-monitor
Use when: comparing counters across several monitors in one panel
Don't: a single monitor (one tab, no ×)
e.g. selected=["xen75","url1"] → two closable tabs
grid-monitor-picker
Use when: choosing/adding a monitor from a rich table (name/ip/type/groups/tags, status, checkboxes)
Don't: a plain name dropdown (that loses the columns/search/multi-select)
e.g. click Select Monitor → the obs-grid-select monitor table
metric-only
Use when: the monitor has no instances / saved views — hide the sub-tabs
Don't: an instance-based monitor (keep Instance)
e.g. views="Metric"
add-drag
Use when: the rows are actions (add to / drag onto a chart), not a value to keep selected
Don't: a single-value picker where the choice persists (use obs-select)
e.g. ⊕ adds the counter (and it disappears from the list); drag it onto a chart to move it out
embedded
Use when: the monitor is already known (a monitor detail screen) — no need to pick/add monitors
Don't: the global metric explorer where the user chooses monitors (leave embedded off)
e.g. embedded counters=[…] → straight to Metric/Instance + the counter list

Composed from labelled DS parts: the MONITOR tabs are obs-tabs (role=tablist/tab; each × is a role=button, aria-label "Close tab", shown only when >1; the + is an obs-button, aria-label "Add monitor"). Select Monitor is obs-grid-select — a searchable, SINGLE-select table with keyboard-navigable rows. The Metric / Instance / Saved View sub-tabs are obs-tabs. Search is a labelled obs-input. Each counter row is a draggable item with a real ⊕ button (aria-label "Add counter") on the left + a decorative drag handle on the right — because native drag-and-drop is pointer-only, the ⊕ is the KEYBOARD-accessible way to add a counter.

Known a11y issues

  • low Counter rows use HTML5 drag (pointer-only). The ⊕ button provides the keyboard / assistive-tech path to add a counter; ensure any drop target also offers a non-drag alternative.
  • low A counter leaving the list (added or dragged) and a monitor-tab switch are visual-only changes — announce them via an aria-live region so screen-reader users track the state.
