Key-Value

The DS key-value / description list (obs-key-value) — the product's column-grid-view / overview-layout: a TRANSPOSED grid where columns become row labels (a tinted label cell) + the record's value. A single-record DETAIL view, common in widget overviews and detail panels. NOT a data table (it only shares the grid chrome) — for rows-of-records use obs-table.

Do

  • Use for a record's detail/overview (label | value).
  • Keep labels short; the label cell is tinted (card variant).
  • Use columns="2" for many fields; colour a threshold value with a --severity token; render a status value as a tag via `status`.

Don't

  • Don't use for tabular records (use obs-table).
  • Don't use for KPI metrics (use obs-metric-list).
  • Don't hardcode a value colour — use a --severity token; don't use 2 columns for long-wrapping values.

Decision flow

  1. Showing ONE record's fields as label→value pairs (a detail / overview panel)? -> Key-Value.
  2. Rows of MANY records with columns? -> the Table (obs-table).
  3. Headline metrics (big number + unit)? -> Metric List (obs-metric-list).

Usage rules

key-value
Use when: a single record's fields shown as label→value pairs (detail / overview panel)
Don't: for tabular records (obs-table) or headline metrics (obs-metric-list)
e.g. a monitor detail panel: Monitor: web-server-01, IP: 10.0.0.12, Type: Linux Server, Uptime: 42 days
card
Use when: the default — a bordered card with a tinted label cell, for a self-contained detail panel/widget
Don't: when the pairs sit inside an already-bordered container or a dense inline overview — use `plain`
e.g. a monitor detail card in a drawer or overview widget
plain
Use when: an inline, borderless detail with muted labels (the overview-layout style) — inside another card/section
Don't: when the block needs its own visual boundary — use `card`
e.g. a properties block inside a larger detail page section
two-column
Use when: a record has MANY fields — columns="2" lays the pairs two-across so it reads compactly (overview-layout 2-columns)
Don't: for a few pairs (1 column is cleaner) or when values are long and would wrap
e.g. an asset inventory panel: Vendor / Model / Uptime / OS / Site / Rack across two columns
color-coded
Use when: a value signals severity/threshold state — pass a `color` (a --severity token) as the item's 3rd field / key
Don't: don't hardcode a hex; don't colour a value with no threshold meaning
e.g. CPU 94% in --severity-critical, Memory 61% in --severity-warning
status
Use when: a value IS a status — pass `status` (e.g. "running"/"down") as the 4th field / key to render it as an obs-tag
Don't: for plain text values (leave status empty); for a big KPI number use obs-metric-list
e.g. Status: a green Running obs-tag inside the detail panel

Semantically a description list — prefer a <dl> if possible; the label cell should be associated with its value. Ensure sufficient contrast on the tinted label cell.
