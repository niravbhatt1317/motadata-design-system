App Header

The GLOBAL top bar present on every authenticated page, and the COMPOSITION HOST for the App Chrome family: the brand/logo on the left, and on the right the interactive surfaces — global search, notifications, and the user account menu — plus a BUILD version tag. Two ways to fill the right side: (1) the INTERACTIVE composition (drop obs-command-palette, obs-notification-menu, obs-user-menu into the slots — each opens its own surface on click; this is how the product's bar works), or (2) the PRESENTATIONAL `actions` prop (declarative circular icon-buttons that fire an `action` event but open nothing — for a simple static header). App CHROME — a SEPARATE archetype from obs-page-header (the per-page title bar); pairs with obs-sidebar (the left module nav). Bar: 50px tall, --page-background-color, a --border-color bottom rule. Circular buttons 36×36 (--neutral-light; --primary when active); notification badge --secondary-red; avatar --primary.

Do

  • Use as the GLOBAL top bar / app chrome on every authenticated page — brand (left) + global actions + user (right).
  • Give an action a `badge` for a live count (notifications / approvals); mark the current-route action `active` (→ --primary).
  • Put an obs-menu in the `user` slot for the account dropdown; a logo <img> in the `brand` slot (theme-toggled).
  • Drive the action buttons from the `actions` prop (reuses obs-icon) and handle clicks via the `action` event.

Don't

  • Don’t use as a per-page header (title + page actions) — that is obs-page-header.
  • Don’t use for the left module/primary navigation — that is obs-sidebar (app-header is the horizontal counterpart).
  • Don’t hand-build the circular icon buttons / avatar — the component renders the chrome; wire routing/search to your app.
  • Don’t place more than one per app — it is the single global chrome.

Where it’s used

  • The top of every authenticated app layout — the global chrome above all page content (layout/header.vue).
  • Left: the product/tenant brand (Motadata logo, or a text wordmark). Right: global search · health monitoring · approval · the notifications bell (with an unread count) · a BUILD version tag · the user account menu.
  • The current-route action highlights --primary (e.g. the Health icon on the health dashboard).
  • Pairs with obs-sidebar (the vertical module nav) to form the app shell; per-page titles/actions live in obs-page-header, not here.

Decision flow

  1. The GLOBAL bar at the very top of every page (logo + global search + notifications + user)? -> obs-app-header.
  2. The per-PAGE title bar (title + count + page actions)? -> obs-page-header, NOT app-header.
  3. The left module/primary navigation? -> obs-sidebar (app-header is the horizontal counterpart).
  4. A left-nav trail / in-page section switch? -> obs-breadcrumbs / obs-tabs.
  5. Want the header to actually WORK (each icon opens a panel)? -> use the INTERACTIVE composition: drop the App Chrome elements into the slots (below), not the `actions` prop.
  6. The global SEARCH / command omnibox (Cmd+K)? -> put an obs-command-palette (overlay) in the default slot — the 🔍 opens a centered modal.
  7. The notifications bell + dropdown panel? -> put an obs-notification-menu in the default slot (it renders its own bell + badge + panel).
  8. The account dropdown from the avatar? -> put an obs-user-menu (turnkey: profile/setup/docs + theme switch + logout) in the `user` slot; for a bespoke list use an obs-menu instead.
  9. Just a simple, non-interactive header (no panels)? -> the `actions` prop (presentational circular icons) + the `user` initials avatar.

Usage rules

interactive-chrome
Use when: the real product top bar — you want clicking search / bell / avatar to actually open their surfaces. Compose the three App Chrome elements in the slots.
Don't: when you only need static icons that fire an event you handle yourself (use `actions`).
e.g. <obs-app-header><obs-command-palette overlay …></obs-command-palette><obs-notification-menu count="3" …></obs-notification-menu><obs-user-menu slot="user" …></obs-user-menu></obs-app-header> — 🔍 opens the Cmd+K modal, 🔔 the alerts panel, avatar the account menu.
presentational-actions
Use when: a simple non-interactive header, or when the surfaces are wired elsewhere and you only need the icon row + an `action` event.
Don't: when you want the panels to open on click — compose the interactive elements instead.
e.g. actions=[{icon:"search",label:"Search"},{icon:"bell",label:"Notifications",badge:3}] + handle @action.
default
Use when: the global chrome of an authenticated app shell — one per app, on every page.
Don't: as a page-level header (title + page actions) -> obs-page-header.
e.g. brand "motadata" + search/health/approval/notifications + BUILD tag + user avatar.
with-badge
Use when: an action carries a live count (unread notifications / approvals).
Don't: a plain action with no count.
e.g. actions=[{icon:"bell",label:"Notifications",badge:3}].
active-route
Use when: highlight the action for the current route/section.
Don't: when no action maps to the current page.
e.g. the Health action is active on the health page ({active:true} → --primary).
logo
Use when: a real product/tenant logo image belongs in the bar.
Don't: when a wordmark/text brand is enough (use the brand prop).
e.g. put <img slot="brand"> (rendered at 40px).
wordmark
Use when: there is no logo image — render the product/tenant name as text (18px / weight 700 / --primary-alt).
Don't: when a logo image exists (use the `brand` slot); the slot wins over the prop.
e.g. brand="ObserveOps".
brand
Use when: leave brand unset to get the DEFAULT ObserveOps logo; set the `brand` slot for a custom logo, or the `brand` text prop for a wordmark.
Don't: expecting an empty brand area when nothing is passed — it now falls back to the ObserveOps mark (like obs-sidebar).
e.g. <obs-app-header></obs-app-header> → shows the ObserveOps logo; <obs-app-header brand="Acme"> → text; <obs-app-header><img slot="brand" src=...></obs-app-header> → custom logo

The bar renders as a <header> landmark. Presentational actions are real <button>s with an aria-label/title (the icon is decorative); the count badge sits inside the button (announced with its label). In the INTERACTIVE composition each slotted element owns its own a11y contract — obs-command-palette manages the Cmd+K modal focus/Esc, obs-notification-menu and obs-user-menu render their own keyboard-navigable popovers with roles — so prefer those over the bare `user` initials avatar (which is only a role=button). One app-header per app; don't nest landmarks.

Known a11y issues

  • low The count badge is a small overlay on the bell — ensure the surrounding button's aria-label conveys the count (e.g. "Notifications, 3 unread") for screen readers, since the visual "3" alone is easy to miss.
