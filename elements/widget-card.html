Widget Card

The dashboard widget CHROME: a framed card with a grey header (title + a hover-revealed time badge + a hover-revealed kebab menu of Full Screen / Share / Edit / Clone / Remove), a body slot for any widget content (chart, gauge, heatmap, table…), the header as a drag handle, and a bottom-right resize grip. The card does not own its position — it emits card-dragstart / card-resizestart (composed, bubbling) so an obs-widget-grid parent can drive the layout, plus an action event for the kebab items.

Events

  • pointer-down on the header (left button, non-static). Bubbles + composed so an obs-widget-grid ancestor can begin a drag. Not emitted when static.
  • pointer-down on the bottom-right resize grip (left button, non-static). Stops propagation (so it is not read as a drag), bubbles + composed for the grid to begin a resize. Not emitted when static.
  • a kebab-menu item was chosen. Emitted as a Vue emit AND dispatched as a composed, bubbling CustomEvent(detail = key). The menu closes on selection.

Slots

  • default — the widget BODY — the actual content the card frames (an obs-severity-heatmap, obs-gauge row, a chart div, a table…). The body area clips overflow and fills the remaining height under the header.

A single widget on a dashboard/monitoring board that must be titled, draggable and resizable within an obs-widget-grid — the repeated chrome every dashboard tile shares.

Do

  • Put the visualization (chart/gauge/heatmap/table) in the default slot; the card is chrome, not content.
  • Give the card a size — inside a grid via the cell (data-x/y/w/h); standalone via an explicit host width + height — or the body has nothing to fill.
  • Use obs-widget-card inside an obs-widget-grid so card-dragstart / card-resizestart actually drive the layout.
  • Set time to the window the widget's data covers (e.g. '1h 12m') so the hover badge is meaningful.
  • Use static on locked / view-only boards or standalone cards to hide the drag/resize affordances.
  • Let the header, badge, kebab and grip inherit theme tokens — don't hardcode the grey header or menu colours.

Don't

  • Don't use obs-widget-card as a generic content card — reach for a plain card for non-dashboard surfaces.
  • Don't wire your own drag/resize handlers onto the card — emit consumers (obs-widget-grid) own that; the card only signals start.
  • Don't render the card with no explicit size and expect the body to show — it needs a footprint.
  • Don't stuff multiple unrelated widgets into one card — one visualization per card.
  • Don't rely on the kebab/time being visible at rest — they are hover-revealed by design; don't put load-bearing controls only there.

Decision flow

  1. Wrapping ONE widget on a dashboard/monitoring board that must be titled + draggable + resizable? -> obs-widget-card, with the visualization in the default slot.
  2. Placing many widgets on a board and want drag-to-move / drag-to-resize? -> put each obs-widget-card inside an obs-widget-grid (it consumes card-dragstart / card-resizestart). The card alone does not move itself.
  3. A framed card that is NOT a dashboard widget (settings panel, summary/KPI tile, a form section card)? -> use a generic card, NOT obs-widget-card.
  4. On a locked / read-only / standalone board where widgets must not move or resize? -> obs-widget-card with static (chrome only, no drag/resize).
  5. Need the chart/gauge/heatmap itself? -> that is a separate element (obs-gauge, obs-severity-heatmap, a chart) placed INSIDE the card's body slot — obs-widget-card never renders data, only the chrome.

Usage rules

default
Use when: a widget sits on an obs-widget-grid dashboard and needs the shared chrome — title header, hover kebab, drag handle, resize grip
Don't: for a non-dashboard card, or when you need the actual chart (that goes in the slot)

The kebab button has aria-label="Widget options"; the resize grip is aria-hidden decoration. Header and badge are text. The menu closes on any outside click across the shadow boundary.

Known a11y issues

  • The time badge and kebab are revealed only on hover / focus-within — keyboard users reach them via focus, but a purely hover reveal is weak discoverability; don't place a widget's ONLY action in the kebab.
  • The kebab menu rows are <a> elements with no href, driven by click — so they are not keyboard-focusable and lack role="menu"/menuitem semantics or a roving tabindex, meaning the menu cannot be operated by keyboard and screen-reader menu navigation is limited.
  • Drag header and resize (grip) are pointer-only (pointerdown, left button) — there is no keyboard affordance to move or resize a widget; arrangement must not be the only path to a task.
