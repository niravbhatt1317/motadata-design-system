The default select control anywhere in the product (single or multi).

Do

  • Use as the standard select; options as { key, text }; v-model the key(s).
  • multiple + allow-select-all for multi; :searchable=false for short lists; trigger slot for custom triggers.

Don't

  • Don't rely on maxAllowedSelection to cap (F2 — use maxValues).
  • Don't assume keyboard/AT users can operate it today (F1). Don't forget searchable/asInput/wrap default true (F3).

Decision flow

  1. Free-form typed tags? -> LooseTags, not the picker.
  2. 2-3 always-visible exclusive options? -> MRadio (segmented).
  3. Simple on/off? -> MSwitch.
  4. Picking a rich RECORD identified by MULTIPLE columns (name/IP/type/status), often multi-select with checkboxes? -> Grid Select (obs-grid-select), not this — its menu is a searchable TABLE, not an option list.
  5. Choosing one/many from a simple {label} list? -> DropdownPicker.
  6. Choosing several? -> multiple (+ allow-select-all).
  7. Short fixed list? -> :searchable=false.
  8. Clearable/none valid? -> allow-clear.
  9. User can add missing options? -> can-user-add-options + add-label.
  10. Options need a VISUAL cue to identify them (a status/severity dot, a type icon, a person's avatar)? -> [element] give each option `severity`/`icon`/`avatar`+`sublabel` (OPTION CONTENT — one rich option schema, NOT a separate component).
  11. Options are HIERARCHICAL (parent/child, e.g. DC > Rack > Server)? -> [element] give options nested `children[]` (tree-select: expand/collapse, branch = subtree select).
  12. How should it OPEN (orthogonal to the above)? -> [element] the `trigger` enum: input (default form field) | text (inline) | button (labelled action, e.g. Columns/Filter) | icon (compact toolbar/kebab/filter, with a count badge) | chip (filter-bar token).
  13. Showing/hiding (and reordering) a TABLE’s columns? -> this Dropdown with a `columns` prop (the column-chooser mode: COLUMNS header + draggable checkbox rows + Reset).

single
Use when: Pick exactly one value from a list — the default and most common mode. Options are { key, text } and v-model binds the selected key. Trigger looks like a form field (asInput) unless overridden.
Don't: Don't use for choosing several values (use `multiple`), for free-form typed tags (use LooseTags), or for 2-3 always-visible exclusive options (use MRadio segmented) or a simple on/off (MSwitch).
e.g. Choosing a monitor type, a template, or an owner; the severity picker; entity pickers like monitor-picker / user-picker / group-picker.
not-searchable
Use when: The list is short and fixed (≤ ~7 items) so the search box would just be noise — set `:searchable="false"` (search defaults TRUE). Used 119×.
Don't: Don't disable search on long or dynamic lists where the user needs to filter — keep the default searchable behaviour there.
e.g. A short fixed enum select such as a status or a small fixed set of options where scanning is faster than typing.
text-only
Use when: The trigger should be plain text rather than a form-field-looking input — set `textOnly` (asInput off). A lightweight, inline-looking trigger. Used 15×.
Don't: Don't use where the control should read as an editable form field (that's the default `asInput` input trigger). For fully custom triggers (button/avatar/pills) use the `trigger` slot instead.
e.g. An inline, label-style select embedded in dense text or a toolbar where a boxed input would be visually heavy.
read-only-pills
Use when: A multi-select is disabled/read-only and you want to display the chosen values as teal SelectedItemPills instead of an editable trigger — the `multiple` + `disabled` presentation.
Don't: Don't use when the user still needs to edit the selection (keep the enabled `multiple` trigger). For an editable single value, use `single`.
e.g. Monitoring Hours shown in a read-only/disabled state renders the selected hours as SelectedItemPills; any disabled multi-select summary.
inline-add
Use when: The user may need a value that isn't in the list yet — set `can-user-add-options` (+ `add-label`) to expose an inline add action in the search area that emits `add`.
Don't: Don't use for a closed/fixed set of options, or for truly free-form typed tags (use LooseTags for that).
e.g. Pickers where the user can create a missing option on the fly (e.g. adding a tag/label that doesn't exist yet) and have it emitted via `add`.
two-pane
Use when: Options need explanatory context — set `useAfterMenuDescription` to render a two-pane layout: the option menu plus a description panel for the hovered item.
Don't: Don't use for simple lists where labels are self-explanatory; the extra description pane is wasted space there.
e.g. A picker where each option needs a hovered-item description to disambiguate choices (e.g. selecting among options whose meaning isn't obvious from the label alone).
use-popover
Use when: Anchor the dropdown with the kit's `MPopover` instead of the default `MPopper` (v-tooltip) — set `usePopover`. Used 26× where the MPopover overlay/positioning behaviour is needed.
Don't: Don't switch off the default unless you specifically need MPopover semantics; the standard trigger uses MPopper by default.
e.g. Pickers embedded in contexts that already rely on the MPopover overlay kit for consistent positioning/stacking.
grid-dropdown (table picker)
Use when: The user picks from RICH RECORDS where each row needs multiple columns to identify it — name + IP + type + status — and often multi-select with checkboxes. The menu is a searchable TABLE, not a plain option list.
Don't: Not for simple {label} options (use the plain dropdown) or a short fixed list. Not for a menu of ACTIONS (that is a Menu / _base-grid-actions, not a picker).
e.g. Select Agent / Select Monitor pickers (~70×): agent, monitor, device, interface, RUM service, integration/SNMP-trap profile, and user selection. Generic base = FlotoDropdownGridSelector (pass your own columns + rows); the monitor/agent variant adds async server-search + row virtualization. Columns: checkbox · Monitor (status ring + name) · IP · Type (product type icons) · Status (status tag). Header sortable; search box on top; selected-count badge + View-All/View-Selected toggles.
icon-dot / severity dropdown
Use when: each option needs a leading GLYPH to be recognised — a severity colour dot, a monitor-type icon, a status colour — shown both per-option and in the collapsed trigger.
Don't: plain text options (use the basic dropdown). If the glyph needs a whole column of context, use the grid dropdown.
e.g. severity-picker (colour dot per severity), monitor-type picker (type icon), status pickers — via the before-menu-text (and after-menu-text) slot. 27 files.
tree-select (hierarchy)
Use when: the choices are HIERARCHICAL (parent → children) and the user navigates by expanding nodes — the codebase has no cascader, this is its equivalent.
Don't: a flat list (basic dropdown) or a multi-column record picker (grid dropdown).
e.g. monitor-hierarchy-picker — Data Centers → sites → monitors, expand/collapse with counts; a leaf is selectable.
avatar / people picker
Use when: the options are PEOPLE — show an avatar (initials/photo) + name so the user is recognised at a glance.
Don't: non-user options. For bulk user assignment across many columns, use the grid-table mode of user-picker.
e.g. owner / assignee / approver / notified-user selection (user-picker.vue, dual list + grid modes).
virtualized rich-row list
Use when: each option is a multi-line CARD (title + meta + glyph) and there can be many — the menu virtualizes tall rows instead of single-line options.
Don't: simple single-line options (basic dropdown).
e.g. notification dropdown (alert cards), widget selector (thumbnails), counter list. 16 files, RecycleScroller.

e.g. standard select
