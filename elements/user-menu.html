The top-right account control of the app shell — the avatar that opens the user's profile links, theme toggle, and Logout. One per app chrome.

Do

  • Place it in obs-app-header's `user` slot (the top-right of the shell).
  • Wire the `logout` event to the sign-out flow and `theme` to your data-theme toggle.
  • Keep the link list short — profile, setup/help, docs; deep settings live in the sidebar.
  • Give the avatar meaningful initials (derived from name) or a real photo.

Don't

  • Don't use it as a generic action menu — that's obs-menu.
  • Don't stuff navigation into it (modules live in obs-sidebar).
  • Don't hardcode colours — the danger Logout uses --secondary-red, rows use tokens.

Decision flow

  1. The header account control (avatar -> profile links + theme + Logout)? -> obs-user-menu, in the obs-app-header `user` slot.
  2. A generic row-of-actions menu (Edit / Delete on a grid row)? -> obs-menu (context), NOT obs-user-menu.
  3. Navigating between modules/sections? -> obs-sidebar / obs-side-menu, NOT a user menu.
  4. Have a user photo? -> set `avatar` (src); else it shows `initials` (derived from `name`).
  5. Restricted context (no theme/logout)? -> theme-toggle="false" logout="false".
  6. Avatar on the left of its container? -> placement="bottom-start".

Usage rules

default
Use when: the standard app-shell account menu — avatar + name/email header, account links, theme toggle, Logout
Don't: for a generic action menu (obs-menu) or navigation (obs-sidebar)
e.g. obs-app-header `user` slot: My Profile / Product Setup Guide / Documentation / Dark theme / Logout
avatar-image
Use when: the user has a profile photo
Don't: no photo — initials read fine and avoid a broken image
e.g. avatar="/uploads/nb.png"
minimal
Use when: an embedded/restricted account menu with just links
Don't: the standard shell (users expect the theme toggle + Logout)
e.g. theme-toggle="false" logout="false"
theme-switcher
Use when: the app offers per-user Dark / Light / Auto — the switcher belongs in the account menu (the product pattern)
Don't: the app has a single fixed theme (theme-toggle="false"); or a global theme control lives elsewhere
e.g. theme="auto" → the Auto segment is active; changing it emits theme:{value} for the consumer to apply
placement-start
Use when: the avatar is positioned so a right-aligned dropdown would overflow — anchor it left
Don't: the standard top-right chrome (bottom-end is correct there)
e.g. placement="bottom-start"
theme-toggle
Use when: you want the account menu to switch the whole UI theme — it works out of the box (no wiring): Dark/Light/Auto flips the document and persists.
Don't: the host app already owns theming — then set manage-theme="false" and handle the `theme` event yourself.
Must: leave manage-theme on by default so anything built with the DS gets a working theme switch; Auto follows the OS.
e.g. <obs-user-menu name="Nirav" theme-toggle></obs-user-menu> → Dark/Light/Auto immediately theme the page.
