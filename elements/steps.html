A task split into an explicit, ordered sequence of stages the user advances through — a wizard, a guided setup, a staged import — where showing progress and completed/remaining steps matters.

Do

  • Use steps only for an ordered, sequential flow — a wizard, not peer sections.
  • Keep `active` in sync with the current stage; let finished/remaining states derive from it.
  • Give each step a short, action-oriented label (Report Properties, Schedule) — add a description in the vertical form.
  • Mark a failed stage with status:"error" so the user sees where it broke.
  • Enable clickable only when revisiting a completed step is actually safe.

Don't

  • Don't use steps to switch between independent sections of one page (that's obs-tabs).
  • Don't use steps for page-to-page navigation (obs-breadcrumbs / obs-sidebar).
  • Don't let a user jump to a future/unreached step (keep them inert).
  • Don't hardcode the state colours — the green/primary/red derive from tokens.

Decision flow

  1. Switching between independent peer sections of the SAME page (Overview / Metrics / Logs)? -> obs-tabs, NOT steps (steps imply an ordered sequence).
  2. Navigating between different pages / a location trail? -> obs-breadcrumbs or obs-sidebar, NOT steps.
  3. An ordered multi-step flow the user advances through (wizard, guided setup, staged import)? -> obs-steps.
  4. Is it a compact horizontal bar at the top of a form? -> direction="horizontal" (the default; the Report wizard).
  5. A side rail with per-step descriptions and back-navigation? -> direction="vertical" + clickable (the compliance form).
  6. Dense/secondary flow where numbers add noise? -> variant="dot".
  7. State: set `active` to the current index; mark a failed stage with a per-item status:"error" (or the `status` prop for the current step).
  8. Want a lighter, outlined circle instead of a solid fill? -> fill="outline".
  9. Want just the progress circles (no labels, no lines) — a compact indicator? -> compact + connector="none" (set completed="green" or "primary").
  10. Should completed steps read GREEN instead of primary/black? -> completed="green".

Usage rules

horizontal
Use when: a wizard with a handful of stages that reads well as a top-of-form progress bar
Don't: steps have long descriptions or there are many of them (use vertical), or the flow isn't ordered (use tabs)
e.g. the Report builder: Report Properties -> Visualizations & Preview -> Schedule
vertical
Use when: a form wizard with a side rail, where each step benefits from a description and the user can jump back
Don't: horizontal space is plentiful and steps are short (a horizontal bar is lighter)
e.g. the compliance Rule form: General -> Rules -> Notification -> Review, in a left MCol rail
dot
Use when: a compact/secondary progress indicator where step numbers would be visual noise
Don't: the user needs to read step labels/numbers to know where they are (use number)
e.g. a dense inline progress track (Ant progressDot style)
clickable
Use when: the flow allows revisiting completed steps (edit an earlier answer) without losing state
Don't: steps must be completed strictly in order and cannot be revisited
e.g. the compliance form lets you click a completed step to go back; future steps stay disabled
outline
Use when: a lighter stepper on a dense page / when a solid filled circle is too heavy
Don't: the default filled circle reads fine (solid has more presence)
e.g. fill="outline" — a transparent circle with a coloured ring + number/✓
circles-only
Use when: a compact progress indicator where labels + lines add noise (e.g. a tight header, a card corner)
Don't: the user needs step names to understand the flow (keep labels)
e.g. compact connector="none" completed="green" — five circles, done ones green, no text/lines
number
Use when: a wizard where users benefit from seeing the step index / a ✓ on completion (the default)
Don't: a dense/secondary track where numbers are noise (use dot) or a bare progress indicator (circles-only)
e.g. variant="number" — 1 / 2 / ✓ circles
error
Use when: a stage FAILED and the user must fix it before continuing (validation error, failed import)
Don't: the step is merely incomplete/pending (that is the wait state, not error)
e.g. items=[{label,status:"error"}] for a specific step, or status="error" for the current step
size
Use when: small (24px) for a dense side rail (the compliance form) or a tight space; default (32px) for a top-of-form wizard bar
Don't: small on a spacious horizontal wizard (the markers look cramped)
e.g. size="small" — the vertical compliance rail
completed
Use when: green when a done/success reading is wanted (a positive completion signal); primary/black for a neutral progress look
Don't: green if the flow is not really success-framed (primary is the safe default)
e.g. completed="green" — done steps read green, the current step stays primary
connector
Use when: line (default) to show the sequence as a connected track; none to drop the lines for a circles-only / segmented look
Don't: none when the sequential relationship between steps must be visually obvious
e.g. connector="none" — used with compact for a circles-only indicator
compact
Use when: space is tight and step names are not essential (a header, a card corner, a toolbar) — show circles only
Don't: the user needs the step labels to understand where they are
e.g. compact connector="none" — five circles, no text, no lines

An ordered progress list: the track is role="list", each step role="listitem", and the current step carries aria-current="step". State is conveyed by more than colour (a ✓ for done, the index for pending, ✗ for error), so it survives colour-blindness and greyscale.
