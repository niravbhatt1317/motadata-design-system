The header omnibox for global/cross-app search or a query-builder command surface — pick a category, type a query, Execute. One per app chrome.

Do

  • Place it in the obs-app-header search area (default slot).
  • Wire `execute` to your search/route and `category` to the scope.
  • Use `error` for parse feedback; keep Execute disabled until the query is valid.
  • Only use it for global/cross-app search — a list filter is the obs-input search type.

Don't

  • Don't use it to filter a single table/list (that's obs-input search).
  • Don't hardcode the categories in the query — the category is a separate scope axis.
  • Don't hardcode colours — the error state uses --secondary-red.

Decision flow

  1. A GLOBAL / cross-app search or a command/query surface in the header? -> obs-command-palette.
  2. A plain search that filters ONE list/table? -> the obs-input `search` type, NOT this.
  3. Is there a category/scope axis (Monitor / Metric / Log)? -> set `categories`; else omit it for a plain bar.
  4. Invalid query? -> set `error` with the message; Execute shows red + is disabled until it clears.
  5. Where does it live? -> the obs-app-header search area (default slot).
  6. Need a full modal Cmd+K palette with a results list? -> compose obs-modal + this bar (route-away); this element is the inline omnibox.
  7. Query has a known vocabulary (metric names)? -> pass `suggestions` for a live autocomplete dropdown.
  8. Results are time-scoped (metrics/logs)? -> `time-range` adds the reused obs-date-time-picker (presets + Custom).
  9. Should the header search open as a focused Cmd+K modal (icon -> centered blurred palette)? -> `overlay`. Inline always-visible bar? -> default (no overlay).
  10. How wide / where? -> default is a 680–800 left-aligned bar; a roomy standalone surface -> `block` (grows to a 1100 cap); center it in its container -> align="center".

Usage rules

default
Use when: the header global-search omnibox — category + query + Execute for cross-app search
Don't: for filtering a single list (use the obs-input search type)
e.g. obs-app-header search area: All / Monitor / Metric + a query + Execute
no-category
Use when: a plain global search with no scope axis
Don't: distinct search scopes exist (add categories)
e.g. omit `categories` -> search + query + Execute
error
Use when: the typed query fails to parse and the user must fix it before running
Don't: the query is valid/empty (no error state)
e.g. error="Unexpected token near '='" -> red Execute + exclamation
with-suggestions
Use when: the query has a known vocabulary (metric names, keywords) worth autocompleting
Don't: a free-text search with no suggestions
e.g. suggestions=['top','system.disk.free.percent',…] → a dropdown while focused
with-time-range
Use when: the query results are time-scoped (metrics/logs over a window)
Don't: a non-temporal search
e.g. time-range → a Last 1 Hour / Last 24 Hours / Custom picker on the right
overlay
Use when: the header search should open the palette as a focused Cmd+K modal (the product behaviour) rather than sit inline
Don't: an always-visible inline search bar is wanted (default mode)
e.g. overlay -> a search icon in obs-app-header; click it -> a centered blurred palette
block
Use when: a roomy standalone search page or a wide header where the 680–800 default feels cramped
Don't: a compact header slot (the default already keeps a min-width 680 so the query is never cramped)
e.g. block -> the bar grows to a bounded 1100px cap
centered
Use when: a standalone / hero search surface where the bar should sit in the middle of its container
Don't: the header search area (left-aligned is the product default)
e.g. align="center" -> the bar centers; the showcase playground uses this
