Layout shells

The 4 route shells (chosen by the src/app.vue switcher + route.meta.layout override) + 2 content layouts that render inside Layout. They differ by chrome: Layout (nav + header + content, the default) · LoginLayout (bare sign-in) · EmptyLayout / PublicLayout (no chrome, padded) · MonitorHierarchyLayout (tree + content) · Settings two-pane (menu + content).

Which page frame to use — almost always the default Layout; switch only for login, print/export, or system (upgrade/restore) pages.

Do

  • Use Layout for in-app pages (default — no route override).
  • Use LoginLayout for auth screens; it's also the not-logged-in fallback.
  • MonitorHierarchyLayout / Settings two-pane render INSIDE Layout — they are content layouts, not route shells.

Don't

  • Don't treat MonitorHierarchyLayout as a route shell (0 meta.layout overrides).
  • Don't add a route layout override unless you need EmptyLayout / PublicLayout.

Where it’s used

  • Layout — ~all authenticated routes (the default).
  • LoginLayout — login / reset / forgot + disk-full + the unauth fallback.
  • EmptyLayout — print-safe report export · PublicLayout — upgrade / restore.
  • MonitorHierarchyLayout — log / inventory / topology (inside Layout) · Settings two-pane — all settings submodules.

Decision flow

  1. Pick the SHELL = the page's top-level skeleton once you know the screen type: list-with-detail, full-page form/record, dashboard canvas, or a centered auth/empty layout.
  2. High-complexity record you must deep-link to / keep in browser history? -> full-page shell (route), NOT a drawer or modal.
  3. Editing a row while keeping the list visible behind? -> keep the list shell + open a drawer (see drawer.json), don't navigate to a new shell.
  4. A quick confirm / small focused task? -> stay on the current shell + modal (see modal.json). Reserve a new shell/route for a whole screen, not an overlay.
