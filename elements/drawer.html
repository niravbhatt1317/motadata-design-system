Detail views, edit forms, and long/record-contextual content that doesn't fit a centered modal.

Do

  • Use a Drawer for detail views, edit forms, long/record-contextual content.
  • Use FlotoDrawerForm for Add/Edit forms (vertical form + footer submit).
  • Put actions in the footer (Cancel left, Save right).

Don't

  • Don't use a Drawer for a short confirmation (use FlotoConfirmModal).
  • Don't rely on backdrop-click to close (disabled) — use the x or footer Cancel.
  • Don't add an MForm inside without suppressing its default Submit (two submit buttons).

Decision flow

  1. Short yes/no or destructive confirmation? -> FlotoConfirmModal, not a drawer.
  2. Long content, a detail view, or a form contextual to a record? -> FlotoDrawer.
  3. An Add/Edit FORM in a panel? -> FlotoDrawerForm (vertical form + validation + footer submit).
  4. A short focused task that must center-interrupt? -> MModal (dialog).

Usage rules

detail(FlotoDrawer)
Use when: view details / long content contextual to a record
e.g. incident details, view-detail/view-more drawers, gauge/compliance drilldown
form(FlotoDrawerForm)
Use when: Add/Edit form in a panel (vertical form + validation; footer Save submits)
e.g. most Add/Edit flows; approval drawers (sync/runbook/firmware), email-dispatch form
width
Use when: default 40%; narrower (px) for simple panels, wider (%) for rich content
e.g. 360px detail, 60% rich editor
large-fullscreen(85-96%)
Use when: complex MULTI-PANE flows (left nav + main form + right reference panel) — config/registration wizards
e.g. APM Application Registration (width=96%); used ~30x at 90%/96%/85%/100%. Use a wide drawer, not a modal.
FlotoDrawer
Use when: You need a slide-in side panel to show the details of a record, or long/rich content contextual to the current context. Open it via the `open` prop (use .sync) or a `trigger` slot; give it a `title`, a scrollable body, and an `actions` footer with `{ hide }`. Default `width` is 40% — narrow to 360px for simple panels, widen to 50-70% for richer editors, or 85-96% for large multi-pane flows (left nav + main form + right reference panel) like config/registration wizards. It's the product's most-used overlay (99x).
Don't: Not for a short yes/no or destructive confirmation (use FlotoConfirmModal), nor a short focused task that should center-interrupt (use MModal). If the panel's whole purpose is an Add/Edit form with validation and a footer Save, reach for FlotoDrawerForm instead so MForm's default Submit is suppressed. Don't rely on backdrop-click to close (maskClosable:false) — use the built-in x or a footer Cancel.
e.g. Incident details panel; view-detail / view-more drawers; gauge / compliance drilldown; credential / catalog selection drawers; APM Application Registration at width=96% (a wide multi-pane drawer, not a modal).
FlotoDrawerForm
Use when: The panel is an Add/Edit FORM. It wraps a vertical FlotoForm with validation inside the drawer and suppresses MForm's default Submit so only the footer Save submits. Provide a `header` (title), fields in the body, and an `actions` footer exposing `{ hide, submit }`. Same open / width / scrolledContent props as FlotoDrawer (59x usage).
Don't: Not for a read-only detail view or non-form content — use plain FlotoDrawer there. Not for a short confirmation (FlotoConfirmModal) or a small center-interrupting task (MModal). Don't hand-roll a bare MForm inside a FlotoDrawer without suppressing its default Submit, or you get two submit buttons — that's exactly what FlotoDrawerForm solves.
e.g. Most Add/Edit flows across the product; sync / runbook / firmware-upgrade approval drawers; attach-rules / attach-storage; the email-dispatch form.
large (multi-pane, 85-96%)
Use when: a rich configuration/registration WIZARD that needs multiple panes (nav + form + info) side by side; too much for a form drawer
e.g. APM Application Registration; multi-pane setup wizards. Use width 85-96% + scrolled-content=false so each column scrolls independently. NOT a modal.
left placement
Use when: a filter or secondary-nav side sheet that conceptually belongs on the LEFT (not a record detail)
e.g. faceted filter panel, left nav drawer. Set placement="left".
footer=close
Use when: a READ-ONLY detail drawer — nothing to submit, just dismiss
e.g. view monitor details, drilldown. Single Close button.
footer=cancel-save
Use when: the STANDARD Add/Edit form — one primary commit
e.g. add/edit a record. Cancel (left) + Save (primary, far right).
footer=reset-cancel-save
Use when: a form where RESET-to-defaults is a common need (filters, config, thresholds)
e.g. filter/config drawers. Reset + Cancel + Save, all right-aligned.
footer=delete-split
Use when: an EDIT drawer where DELETING the record is a primary, destructive action that must be visually separated from Save
e.g. edit + delete a policy/monitor. Delete (error outline) on the LEFT via justify-between; Cancel + Save on the right.
footer=note-split
Use when: a multi-step form (needs Back) or a form that must surface a mandatory-fields note on the left
e.g. wizard step, mandatory-field form. Note or Back on the LEFT; confirm group (Cancel/Save) on the right. 4+ actions → move extras into a menu.
inset-alignment
Use when: the heading, body and footer share ONE horizontal inset (--drawer-inset, default 15px) so they ALIGN. Set the `--drawer-inset` custom property on the drawer for any value; `use-padding` bumps all three to 24px together.
Don't: expecting `use-padding` to pad only the body — it now widens the WHOLE panel (header+body+footer) so they stay aligned.
e.g. <obs-drawer style="--drawer-inset: 20px"> aligns all three regions at 20px; use-padding → 24px
