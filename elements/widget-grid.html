Widget Grid

A live draggable / droppable / resizable dashboard grid — the framework-agnostic answer to vue-grid-layout. Slot in obs-widget-card children carrying data-x/data-y/data-w/data-h; the grid snaps each to a 12-column layout, pushes colliding cards down, compacts everything up under gravity, and auto-scrolls the page while you drag or resize a card past the fold. Emits layout-change with the settled positions.

Events

  • Fired once per gesture, on drop. The grid also writes the new values back onto each card's data-x/data-y/data-w/data-h attributes, so you can persist either the event payload or read the attributes. Use it to save the board and to reflow chart widgets that only auto-size on width.

Slots

  • default — obs-widget-card children, each with data-x / data-y / data-w / data-h attributes (column/row origin + width/height in grid units; defaults 0/0/4/3 if omitted). The grid assigns every card an internal `slot="cN"` and positions it via a wrapper in its own shadow DOM — never position or transform a card yourself. A MutationObserver re-syncs when cards are added or removed.

A user-arrangeable board of widgets — a monitoring dashboard, a report canvas, any surface where the end user drags and resizes cards and you save where they land.

Do

  • Make every child an obs-widget-card with data-x / data-y / data-w / data-h (column/row origin + size in grid units).
  • Give the grid a block container with a real width — column width is measured from it via ResizeObserver.
  • Ensure the intended scroll container (the ancestor with overflow:auto/scroll) is the one that scrolls, so edge auto-scroll can drag cards past the fold.
  • Listen to layout-change to persist the board and to reflow chart widgets (e.g. Highcharts only auto-sizes on width, so reflow taller cards on the size change).
  • Let the grid own positioning — read the settled positions from the event detail or the cards' data-* attributes after a gesture.

Don't

  • Don't nest a widget grid inside another widget grid.
  • Don't position or transform the cards yourself (set left/top/transform) — the grid places each one via its own shadow-DOM wrapper; positioning a slotted element directly is buggy across browsers.
  • Don't put non-obs-widget-card elements as direct children expecting placement — only obs-widget-card children are synced into items.
  • Don't fight the compaction — cards gravity-compact upward; encode intent in data-x/data-y, not in CSS.

Decision flow

  1. Does the END USER rearrange the layout at runtime (drag cards, resize them, and expect it to stick)? -> obs-widget-grid.
  2. Is the layout authored by YOU and never rearranged by the user? -> a static CSS grid (display:grid) — don't pull in drag/resize machinery you won't use.
  3. Do you just need ONE resizable/movable panel (not a board of them)? -> a split/panel primitive, not a grid.
  4. Building the children: each widget is an obs-widget-card (it emits card-dragstart from its header and card-resizestart from its bottom-right handle — that's what the grid listens for). Give the grid a block container with a real width so column math resolves.
  5. Need cards draggable past the fold? -> the grid already auto-scrolls the nearest scrollable ancestor; just make sure that ancestor is the scroll container (overflow:auto/scroll).

Usage rules

12-column (default)
Use when: you want the product's standard board — leave columns at 12 so every widget's data-x/data-w reads on the same lattice the rest of the product uses, and cards line up across dashboards
Don't: the surface is a narrow panel or a wide wall where 12 units are too fine or too coarse (drop to a custom column count instead)
e.g. <obs-widget-grid> (no columns attr) wrapping the Alert-Summary gauges, heatmap and pie cards on the default 12-wide grid
custom columns
Use when: the board's width or density needs a different lattice — columns="6" for a narrow side panel, a higher count for a wide wall board — so card footprints snap sensibly to the available width
Don't: the placement expresses cleanly on 12 columns (keep it 12 for cross-dashboard consistency)
e.g. <obs-widget-grid columns="6"> for a compact side panel of stat cards
custom cell height / gap
Use when: the widget density on this board needs taller/shorter rows or tighter/looser gutters grid-wide — set cell-height and gap once instead of resizing every card
Don't: only one card needs to be taller (change that card's data-h — cell-height/gap are grid-wide, not per-card)
e.g. <obs-widget-grid cell-height="78" gap="10"> to match the Alert-Summary row rhythm
user-arrangeable-dashboard
Use when: the user builds/edits their own board — drag widgets, resize them, and you save the layout
Don't: the layout is fixed and code-authored (use a CSS grid) — the drag/resize/collision logic is dead weight there
e.g. the Alert-Summary board: gauges, an infrastructure heatmap and pie widgets the user hand-arranges
custom-columns
Use when: a denser or coarser lattice suits the surface — columns="6" for a narrow panel, more columns for a wide wall board
Don't: you can express the placement on the standard 12-column grid (keep it 12 for product consistency)
e.g. a compact side panel of stat cards on a 6-column grid
cell-height-gap
Use when: you need taller rows or tighter/looser gutters for the widget density on this board
Don't: resizing an individual card would do (that's the card's h, not a grid-wide change)
e.g. cell-height="78" gap="10" on the Alert-Summary board

A pointer-driven drag/resize surface — flag the keyboard gap honestly. The grid moves and sizes cards from pointermove/pointerup, driven by card-dragstart / card-resizestart (pointer gestures on the card); it does not currently expose a keyboard path for rearranging or resizing, nor announce gesture state to assistive tech. Positioning is presentational, so a board stays READABLE by content even though it is not REARRANGEABLE by keyboard.

Known a11y issues

  • No keyboard alternative for drag/move or resize — rearranging is pointer-only (card-dragstart / card-resizestart come from pointer interactions).
  • Drag/resize state is not announced to assistive technology — no aria-live feedback on move, resize, or drop.
  • The dashed placeholder is a purely visual affordance (aria-hidden by nature) — an AT user gets no equivalent preview of where a card will land.
  • Edge auto-scroll moves content under the pointer only; there is no keyboard-triggered scroll-into-view for an off-screen card during a (would-be) keyboard rearrange.
stable
  • 2026-09-07 — Added obs-widget-grid: live drag/drop/resize dashboard grid — grid snap, collision push-down, gravity-up compaction, edge auto-scroll with scroll-compensated drag math, layout-change events. Positions obs-widget-card children (data-x/y/w/h) via shadow-DOM wrappers + named slots. Powers the Alert-Summary board.
  • Keyboard-only users cannot rearrange or resize cards — the gesture is pointer-driven (card-dragstart / card-resizestart come from pointer interactions on the card).
  • Resize height is capped at MAX_H = 40 rows — a safety cap so a held auto-scroll during resize can't grow a card without bound; a card cannot be resized taller than 40 row-units regardless of drag distance.
  • Edge auto-scroll targets the NEAREST scrollable ancestor (first ancestor with overflow-y auto/scroll AND real overflow); if the real scroll container isn't a scrollable ancestor of the grid, dragging past the fold falls back to the document scroller and may not move the intended region.
  • Only direct obs-widget-card children are managed; other elements slotted in are ignored by the layout engine (not positioned, not compacted) — put charts/gauges/heatmaps INSIDE a card's default slot, not as grid children.
  • Column width is measured from the host via ResizeObserver, so the grid must have a real, non-zero rendered width before cards can be placed sensibly (an unsized/display:none container collapses cellW to its 1px floor).
  • Chart widgets that only auto-size on width (e.g. Highcharts) leave empty space below a card that was resized TALLER — reflow them from the layout-change event (and/or a per-card ResizeObserver), the grid does not reflow card bodies for you.
  • Nesting a widget grid inside another widget grid is unsupported — the inner grid's cards would be double-managed.
